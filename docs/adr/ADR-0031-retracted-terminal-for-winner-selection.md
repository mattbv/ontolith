# ADR-0031: Retraction and Supersession Are Terminal for `resolve_contradiction()` Winner Selection Too

**Status**: Accepted
**Date**: 2026-08-19
**Deciders**: Ontolith Core Team
**Related**: SPEC §10.3 (contradiction resolution), KI-026 (self-resolution guard), KI-033 (retract party-to-contradiction guard), KI-034 (retracted stays terminal across extension), KI-044, KI-045 (flag_contradiction() reads status before its transaction — a race that can undo the same terminal-status guard this ADR relies on flag_contradiction() already applying correctly), KI-050 (flag_contradiction() can open a contradiction with no eligible winner among its founding members — found during this ADR's own review, filed separately), KI-051 (retract() can still overwrite a superseded member, bypassing the KI-033/KI-043 guards — found in a later review pass, filed separately)

---

## Context

`resolve_contradiction(contradiction_id, winner_assertion_id, resolver)` gates winner eligibility purely on `winner_assertion_id in contradiction.member_ids` (SPEC §10.3) — it does not check the candidate's current `status`. Since KI-034, a `retracted` member's id deliberately stays in `Contradiction.member_ids` (that list doubles as `_reject_retract_if_party_to_contradiction`'s scan set, not audit-only), so a resolver could pick an already-`retracted` member as the winner: its status flips to `active` (the `self.backend.set_assertion_status(winner_assertion_id, "active")` line), the value reappears in default query results, but `valid_to` stays closed at the original retraction time — an `active` assertion with a closed `valid_to`.

That specific combination is not, on its own, impossible to produce elsewhere — an author-supplied `valid_from`/`valid_to` window on an ordinary `assert_literal`/`propose` call produces `active` + a set `valid_to` too, when the author is declaring a fact's *known* end of validity up front. What's actually wrong about reactivating a `retracted` (or, as review surfaced during this fix, `superseded`) member is narrower and more specific: it silently *undoes a governance action's close* of that window — the retraction/supersession event that terminalized the assertion — without any new write recording that the window reopened. The closed `valid_to` stays attributed to whatever originally closed it (a `retract()` call, or a later value superseding it), now contradicted by a `status=active` that implies otherwise. That mismatch between what `valid_to` says happened and what `status` now claims is what nothing else in this codebase produces by construction.

This is pre-existing, not introduced by KI-034, but KI-034 is what makes a `retracted` member persist inside an *open* contradiction long enough for a resolver to plausibly reach this path — before that fix, an extension would have already resurrected it back to `flagged`, an equally wrong but different outcome. Found during KI-034's own review (2026-08-05).

**Review of this ADR's first version found the fix needed to cover `superseded`, not just `retracted`, and needed a second call site fixed alongside `resolve_contradiction()` itself** — the codebase already had an established but *incompletely applied* principle:

- `flag_contradiction()` already treats `retracted`/`superseded` as terminal for its own re-flag write (its existing comment: "flagging an assertion explicitly named here must not resurrect one"). It also, by design, accepts a `superseded` (or `retracted`) assertion as one of the two assertions named in the call — its own comment: "a flagged/superseded assertion must still be resolvable here, e.g. when extending an open contradiction." That means a `superseded` assertion (one whose predicate was `time_varying` at write time, or became so after a schema change) can legitimately end up as a `Contradiction` member, with its status left untouched at `superseded` — never `flagged`.
- `_apply_with_conflict_routing`'s `Contradict` extension branch (KI-034) only skipped re-flagging a `retracted` member, not a `superseded` one — so extending an open contradiction with a new conflicting value would flip a `superseded` member's status back to `flagged`, un-terminalizing it. A `resolve_contradiction()` winner check that only looked for `retracted` would then miss it entirely once that flip happened, or would miss it directly if a resolver picked the still-`superseded` member as winner before any extension occurred.

Both gaps are closed together here, since neither closes KI-044 on its own — a check for `retracted` alone in `resolve_contradiction()` is not sufficient while `superseded` reaches the same member-eligible, non-`flagged` state through `flag_contradiction()`, and is not *durable* while the extension branch can still flip a `superseded` member back to `flagged` regardless of what `resolve_contradiction()` checks.

## Decision

Two changes, both treating `retracted` and `superseded` as the same terminal category:

1. **`resolve_contradiction()`** now rejects a winner candidate whose current status is `retracted` *or* `superseded` with `ValidationError`, mirroring the existing "winner not a member" check's exception type. The check runs only *after* the full party-to-contradiction loop has passed for every member (see Rationale on ordering), reusing the already-fetched winner `Assertion` rather than a second lookup.
2. **`_apply_with_conflict_routing`'s `Contradict` extension branch** (the KI-034 fix) now skips re-flagging a member whose status is `retracted` *or* `superseded`, not just `retracted` — closing the path where extending an open contradiction could un-terminalize a `superseded` member.

A resolver who wants a terminal member's value active again has no path via `resolve_contradiction()` — they must submit it as a new assertion instead (which flows back through ordinary SPEC §10 conflict routing).

## Rationale

**Why reject rather than silently reactivate:** see Context — reactivating a terminal member doesn't just produce an unusual field combination, it silently contradicts what the assertion's own `valid_to` (set by the governance action that terminalized it) still records. An `active` assertion whose `valid_to` was closed by something *other* than the write that made it active again is exactly the kind of state a reader (or a downstream bitemporal `as_of()` reconstruction) has no established way to interpret — it isn't "currently valid" the way `valid_to IS NULL` normally means, and treating it as valid-until-`valid_to` again would silently resurrect a fact-shaped statement whose validity window a governance action already closed, without any record of *why* it's now open again.

**Why `retracted` and `superseded` together, not just `retracted`:** both are "closed by a governance/routing action, not by the author declaring an end date" — the same category the previous paragraph's distinction is about. Treating only `retracted` as terminal (this ADR's first draft) left an identical bug reachable through `superseded`, via `flag_contradiction()`'s own by-design acceptance of a `superseded` assertion as a contradiction member — found in review, not anticipated when the narrower version was first written.

**Why this is "retraction/supersession is terminal," not a new rule:** KI-033 and KI-034 already established the principle (for `retracted`) in two other paths (self-retraction after being flagged, and contradiction extension); `flag_contradiction()` already independently applied it to *both* statuses for its own re-flag write. This ADR makes the principle consistent across every place `resolve_contradiction()` itself, and the write paths that decide what status a contradiction member ends up with, are concerned — the winner check, the loser loop (found in a later review pass — see Consequences), and the `_apply_with_conflict_routing` extension branch that had only ever been updated for `retracted`. It does **not** reach every place a member's status can change at all: `retract()` itself still doesn't recognize a `superseded` member as governed the same way it does a `flagged` one, a gap found later and tracked separately as KI-051 rather than folded into this already-multi-round fix.

**Why the winner-status check runs only after the full party-loop, not inline with it:** an earlier version checked `member.status` inline, in the same per-member loop as the party check, the moment it reached the winner's `member_id` — which made the *order* of `CapabilityError` (party) vs. `ValidationError` (terminal status) depend on where the winner happened to fall in `contradiction.member_ids`' iteration order, if the resolver was disqualified both ways at once. Being a party is the stronger, more fundamental disqualification (SPEC's self-resolution concern, KI-026), so it should always be reported first regardless of member order. The loop now only captures the winner `Assertion` object as it iterates (still raising immediately for any party violation, on any member); the terminal-status check runs once, after the loop completes without a party violation, using the captured object — no extra lookup, and deterministic precedence.

**Why `ValidationError`, not `CapabilityError`:** mirrors the existing "winner not a member" check immediately above it in the same method — both are about the *shape of the request* (naming an ineligible candidate), not about who's asking. The self-resolution guard (party/AI-kind) stays `CapabilityError` since that's about the resolver's own standing, a genuinely different kind of failure.

**Why no path to "un-terminalize and reactivate" is offered:** a deployment that wants a terminal value active again has an unambiguous, already-existing route — assert it again. That new assertion goes through ordinary SPEC §10 conflict routing (superseding or re-flagging as appropriate) rather than reaching into `resolve_contradiction()`'s narrower "pick among these specific members" contract to special-case a resurrection.

## Consequences

**Positive:**
- Closes KI-044 for real: `resolve_contradiction()` can no longer produce an `active` assertion whose `valid_to` still records a governance-action close, via either `retracted` or `superseded`, and the one adjacent path (contradiction extension) that could un-terminalize a `superseded` member first is closed too. The loser loop (`resolve_contradiction()`'s own write of every non-winner member) was a third site needing the same widening, found in a later review pass and closed in the same fix — it now skips a `superseded` loser the same way it already skipped a `retracted` one, rather than overwriting it to `retracted` and recording a misattributed event.
- Deterministic error precedence: a resolver who is both a party and picks a terminal-status winner always sees `CapabilityError`, never `ValidationError`, regardless of `member_ids` ordering.

**Negative / follow-ups:**
- **Behavior change**: a resolver who was relying on picking an already-`retracted` or already-`superseded` member to reactivate it now gets `ValidationError` instead. Flagged `**Breaking:**` in CHANGELOG per ADR-0019's policy, despite no public signature change, matching the same class of behavior-level break ADR-0030 (KI-043) was flagged for.
- **A contradiction whose every *existing* member is `retracted`/`superseded` has no eligible winner until a fresh assertion joins it — not a permanent dead end, but not free either.** Every current member now fails the winner check, and there is no other way to close a `Contradiction`'s `state` without one more write landing first. `_reject_retract_if_party_to_contradiction` keeps applying to it, and — per KI-043/ADR-0030's own routing — retracting *any* remaining flagged member of it now goes through the same review-gated path, which can itself only ever produce more terminal members, never fewer.

  **The escape hatch is `predicate`-shape-dependent, found in review to not be the single uniform story an earlier draft of this ADR claimed.** Contradictions *auto-detected by conflict routing* can only arise on `static` predicates (SPEC §10.1) — but `flag_contradiction()` itself is not restricted to `static` predicates, and is exactly how a `superseded` member (which only ever arises on a `time_varying` predicate) becomes a contradiction member in the first place. For a `static` predicate, asserting the intended value again is enough: `_apply_with_conflict_routing`'s `open_contradiction is not None and temporality == "static"` shortcut (`ontology.py`) unconditionally extends the *same* open contradiction with the fresh assertion as a new `flagged` member, regardless of whether every existing member is already terminal — no special-casing needed, this is just what extension already does. But for a `time_varying` predicate, that same shortcut never applies (it's gated on `temporality == "static"`); a fresh assertion instead reaches `route()`, finds no `active` existing assertion to conflict with (every member is terminal), and comes back `Activate` — `status="active"`, **not** added to `member_ids`. The actual remedy there is `flag_contradiction(fresh_assertion_id, any_existing_member_id, ...)`, which accepts a fresh `active` assertion the same way it already accepts a `superseded` one, extends the same contradiction, and flips the fresh assertion to `flagged` — at the cost of demoting a live `active` assertion back into dispute, a different, more deliberate action than "just assert it again." Not fixed here (see the next bullet); the two-mechanism story itself is the accepted state, not a defect, but callers relying on a `time_varying` predicate need to know `flag_contradiction()`, not a bare re-assert, is what actually reopens the path.
- **`flag_contradiction()` itself can create a contradiction whose two founding members are already both terminal, with no eligible winner among them from the moment it's created** — it validates subject/predicate agreement but not member eligibility, and both statuses are explicitly accepted by design (see Decision). Reachable at only `propose` capability, including by an AI principal over MCP (`ontolith.flag_contradiction` carries no write capability at all). This is *not* permanently unresolvable (the same fresh-assertion escape hatch above applies — an earlier draft of this ADR, and of the KI it's tracked under, said otherwise, corrected in review) — but a caller has to know to do that extra write before `resolve_contradiction()` can succeed at all. Not addressed by this ADR — tracked separately as KI-050, since it's a `flag_contradiction()`-specific eligibility question (should it validate that *at least one* named assertion is currently `active`/`flagged`?), not a consequence of how `resolve_contradiction()` picks winners.
- **`retract()` itself doesn't recognize a `superseded` contradiction member as governed the way it does a `flagged` one — found in a later review pass, not closed by this ADR.** `_reject_retract_if_party_to_contradiction` (KI-033) and the KI-043/ADR-0030 capability-floor check both early-return for any target whose status isn't `flagged`, which was safe before this ADR (a member could only be `flagged` or `retracted`, and `retract()` is already a no-op on an already-`retracted` target) but isn't now that `superseded` is a designed, documented status a contradiction member can hold while its contradiction is open. A party to the dispute, at only `write` capability, can retract a `superseded` member directly — no party guard, no review/admin floor. This doesn't reopen KI-044 itself (the result is still terminal, so the winner check still rejects it), but it does let `status` stop recording *how* the assertion actually became terminal, and lets exactly the principal KI-033 exists to block cause that. Tracked separately as KI-051.
- A resolver hitting the all-terminal case now has to author a fresh assertion for the value instead of reactivating an old one — a minor ergonomic cost, accepted as the correct tradeoff for not reintroducing a semantically ambiguous state.

## Alternatives Considered

**Silently skip an already-terminal candidate and require the resolver to pick a different member:** Rejected — picking a *different* winner than the one requested without telling the caller is a worse failure mode than a clear, immediate `ValidationError`; every other ineligibility check in this method (not a member, resolver is a party) fails loudly rather than silently substituting.

**Allow reactivation but also reopen `valid_to` (set it back to `None`):** Rejected — this would make `resolve_contradiction()` implicitly perform two actions (pick a winner, *and* undo a prior terminalization's temporal close) through one call with no explicit signal that the second thing happened; a resurrection is significant enough it should show up as its own explicit write (a fresh assertion), not a side effect of winner selection.

**Add an admin-only way to force-close a fully-terminal, unresolvable contradiction:** Rejected for this ADR's scope — see Consequences. No deployment has asked for it yet, and it's a new capability/state, not a gap this fix's own principle (retraction/supersession is terminal) implies.
