# ADR-0036: RDF/OWL Bridge — `rdflib`-Backed, Schema + Active-Assertion Instance Data, Export Only

**Status**: Accepted
**Date**: 2026-08-27
**Deciders**: Ontolith Core Team (rdflib dependency and export scope confirmed with the user directly, given the explicit "confirm at M3" framing the Implementation Plan already carried for this kind of decision)
**Related**: SPEC §13.3 (interop bridge sequence — LinkML → RDF/OWL → agent-memory), SPEC §6.1 (one IR, two front-ends), ADR-0013 (LinkML dialect coverage — the precedent this ADR mirrors and the "no real `linkml`/`linkml-runtime` dependency" decision this ADR extends the reasoning of), ADR-0015 (plugin capability isolation — `ReadOnlyView`, `Exporter` protocol), ADR-0017 (cardinality), ADR-0028 (`required` stays out of core — referenced for why this bridge doesn't encode it as an OWL restriction), Implementation Plan §2/§14 (M3 scope, "GraphQL and the RDF/OWL bridge not started")

---

## Context

M3's scope column has named an RDF/OWL bridge since the Implementation Plan's first draft, alongside the already-shipped LinkML YAML bridge (ADR-0013) and GraphQL (still unstarted — a separate, independent decision, not this ADR's concern). SPEC §13.3 fixes the bridge shipping order — LinkML → RDF/OWL → agent-memory — and states the RDF/OWL bridge "MAY initially delegate to LinkML's RDF emission," which reads two ways: (a) literally, meaning use the real `linkml`/`linkml-runtime` package's own `RDFGenerator`, or (b) in spirit, meaning produce the same *shape* of RDF/OWL output LinkML's tooling would, without necessarily depending on that specific toolchain.

ADR-0013 already answered the adjacent question for the YAML bridge: it explicitly rejected depending on the real `linkml`/`linkml-runtime` packages for v1, because they're heavy (pull in `rdflib`, `prefixcommons`, JSON-LD context machinery) for a deliberately scoped-down dialect, and full LinkML conformance was never the v1 goal (SPEC §6.1's "strict subset/superset" framing). Re-litigating that decision now, in the opposite direction, for the RDF/OWL bridge specifically wasn't obviously right or wrong without checking — `rdflib` alone (not the full `linkml`/`linkml-runtime` stack) is a much lighter, standard, focused Python RDF library that produces correct RDF/OWL output (proper URI/namespace/datatype handling) without the rest of the LinkML toolchain's weight.

## Decision

**Library: add `rdflib` as a new dependency**, in the same `interop` optional-dependency group `pyyaml` (the LinkML bridge's own dependency) already lives in — not the real `linkml`/`linkml-runtime` packages, and not a hand-rolled Turtle/RDF-XML string builder. `rdflib` builds the OWL ontology as a real `rdflib.Graph` and serializes it via `rdflib`'s own writers (Turtle by default; any format `rdflib` supports — RDF/XML, N-Triples, JSON-LD if the optional plugin is present — works via a `format` parameter), producing genuinely well-formed, parseable RDF rather than string output that merely looks like RDF.

**Scope: schema (OWL ontology) AND active-assertion instance data (RDF individuals), export only.**

- `src/ontolith/schema/rdf.py::to_owl(schema: SchemaIR) -> Graph` — the schema half, mirroring `schema/linkml.py::to_yaml`'s exact shape (pure function, no KB dependency, easily unit-testable). Each `ConceptDef` becomes an `owl:Class`; each `PropertyDef` becomes an `owl:DatatypeProperty` (range mapped to XSD via `value_type_to_xsd`); each `RelationDef` becomes an `owl:ObjectProperty` (range the target concept's class, `owl:inverseOf` the target's own `inverse`-named property if declared). `cardinality="single"` (the schema default, ADR-0017) is additionally typed `owl:FunctionalProperty` — the standard OWL idiom for "at most one value," needing no cardinality-restriction blank nodes. `required` is deliberately **not** encoded as an `owl:minCardinality` restriction, consistent with ADR-0028's stance that `required` is validator-backed policy, not a structural core/schema-layer constraint.
- `src/ontolith/plugins/reference/rdf_exporter.py::RdfExporter` — a new reference `Exporter` plugin (SPEC §13.2) reusing `to_owl`'s graph and IRI-minting helpers, adding one `rdf:type` triple per distinct entity seen and one property triple per active assertion (literal → datatype-property triple with the correct XSD datatype; ref → object-property triple). Read-only, matches `JsonExporter`'s existing shape and scope exactly (active assertions only, no historical/flagged/retracted data — `ReadOnlyView.assertions()`'s own default).
- **Export only.** There is no `from_owl`/import direction in v1. Reading arbitrary external OWL back into Ontolith's own deliberately simple property/relation model is a substantially larger, separate problem (unbounded OWL expressivity — class hierarchies, restrictions, unions, equivalence — against a schema model with none of those concepts) than emitting it, the same class of scope boundary ADR-0013 already drew for the YAML dialect (documented subset, not full conformance). Left as an explicit future decision, not silently dropped — SPEC's `Importer`/`Exporter` protocols already exist and would house it if built.

**IRI scheme: deterministic, `urn:`-based, namespace-derived only.**

```
Ontology:  urn:ontolith:{namespace}:
Class:     urn:ontolith:{namespace}:class:{ConceptName}
Property:  urn:ontolith:{namespace}:property:{ConceptName}.{fieldName}
Instance:  urn:ontolith:{namespace}:entity:{entity_id}
```

`urn:` IRIs, not `http(s):` ones — Ontolith has no fixed, resolvable public host to mint real web IRIs under, and fabricating one (e.g. `https://ontolith.example/...`) would look like a real, dereferenceable domain when it isn't. `urn:` IRIs are valid RDF/OWL subjects and predicates without implying network resolvability. Property IRIs reuse the same dotted `"Concept.field"` string already used everywhere else in this codebase (`Assertion.predicate`, `SchemaIR.value_type_of()`, ...), keeping a triple's predicate IRI directly traceable back to the predicate that produced it.

Deliberately does **not** consult `SchemaIR.metadata["default_prefix"]`/`["prefixes"]` — preserved verbatim on a LinkML-imported schema (ADR-0013) for exactly this kind of purpose, but interpreting that free-form, "not interpreted" (per ADR-0013's own framing) metadata blob defensively would be real, non-trivial complexity for a v1 slice. Honoring an imported LinkML schema's own declared prefixes for RDF/OWL export is a reasonable, explicit follow-up, not implemented here.

**`Ontology` and `ReadOnlyView` both gain a new `schema()` method.** `RdfExporter` needs the active `SchemaIR` to derive OWL classes/properties, and no existing plugin view exposed schema access at all (every prior reference plugin only ever needed entity/assertion data). `Ontology.schema()` (mirroring the existing `AsOfView.schema()`) returns `self.backend.get_schema(self.namespace)`; `ReadOnlyView.schema()` delegates to it — `self._kb.schema()`, not `self._kb.backend` directly (an earlier version of this fix reached into the storage port directly from the view, the only view method that did; found in review — every other `ReadOnlyView` method delegates to an `Ontology` method, per this module's own "safe method subset of Ontology" framing). Schema is namespace-scoped, non-sensitive metadata with no principal-specific governance concern the way write access is, so no capability narrowing was needed beyond what `ReadOnlyView` already provides.

**Not bundled into `plugins/reference/__init__.py`'s eager imports**, unlike the three existing reference plugins there. Python always initializes a parent package before any of its submodules — including when a single plugin is loaded by name via its own entry point (`PluginRegistry.register()` → `entry_points(...).load()`) — so if `RdfExporter` were added to that `__init__.py`'s import list, using *any* reference plugin (including `CsvImporter`/`JsonExporter`/`RequiredFieldsValidator`, none of which need `rdflib`) would require `rdflib` installed. `RdfExporter` is still registered as a real `ontolith.plugins` entry point in `pyproject.toml` (`entry_points()` enumeration is metadata-only and doesn't import anything until a specific entry point's `.load()` is called, verified before relying on this), just imported directly (`from ontolith.plugins.reference.rdf_exporter import RdfExporter`) rather than via the package's convenience re-export.

## Rationale

**Why `rdflib` and not the real `linkml`/`linkml-runtime` packages:** `rdflib` alone doesn't pull in `prefixcommons`, JSON-LD context machinery, or the rest of the LinkML schema-processing toolchain ADR-0013 found disproportionate to a deliberately scoped-down dialect — it's specifically an RDF graph/serialization library, nothing more. Depending on the full `linkml` package here, just to reach its RDF generator, would reopen exactly the dependency-weight question ADR-0013 already closed for the adjacent bridge, for no corresponding gain: this bridge's own scope (SchemaIR → OWL classes/properties, active assertions → RDF individuals) doesn't need LinkML's own schema model or `SchemaView` machinery at all — it starts from `SchemaIR`, the same IR every other bridge does.

**Why not hand-roll RDF/Turtle text** (matching `schema/linkml.py::to_yaml`'s own plain-string-building approach): RDF/OWL correctness depends on details a plain string builder gets subtly wrong without real effort — URI escaping in Turtle's compact syntax, proper `xsd:` literal datatype tagging, prefix-declaration consistency, blank-node syntax if ever needed. `rdflib`'s writer already handles all of this correctly, and using it costs one moderate, focused dependency rather than reinventing an RDF serializer. `to_yaml`'s hand-rolled approach works for YAML because YAML's syntax is comparatively forgiving and PyYAML already exists as the parsing counterpart; RDF/Turtle doesn't have the same safety margin.

**Why schema AND instance data, not schema-only** (which would have mirrored `to_yaml`'s own schema-only scope more closely): confirmed directly rather than assumed — an OWL ontology with no instance data is a valid, standalone interop artifact (e.g. importable into Protégé for schema alignment) but a full RDF/OWL export that also carries the KB's actual data is a materially more complete, more immediately useful v1 deliverable, and the added implementation cost (reusing `to_owl`'s own IRI helpers, iterating `kb.assertions()` exactly like `JsonExporter` already does) was judged proportionate.

**Why the IRI scheme doesn't consult `metadata["prefixes"]`:** that metadata is explicitly "preserved verbatim, not interpreted" per ADR-0013 — it has no validated shape this bridge could safely assume without adding real defensive-parsing complexity for a feature (prefix-aware IRI minting) not requested and not blocking a useful v1. A `urn:ontolith:{namespace}:...` IRI is deterministic, requires zero configuration, and is valid regardless of whether the schema came from the class DSL, hand-built `SchemaIR`, or LinkML YAML.

**Why `owl:FunctionalProperty` for `cardinality="single"` but nothing for `required`:** `owl:FunctionalProperty` is a simple, standard OWL type declaration — no cardinality-restriction blank nodes needed, and it's a faithful translation of what `cardinality="single"` already means structurally (SPEC §6/ADR-0017: a predicate declared `single` may have at most one *currently-active* value). `required` has no equally clean translation and, per ADR-0028, is deliberately validator-backed policy rather than a structural core constraint in this codebase at all — encoding it as `owl:minCardinality 1` here would assert a structural guarantee the core layer itself doesn't actually enforce, which would be actively misleading to a consumer of the exported ontology.

## Consequences

**Positive:**
- Closes the RDF/OWL half of M3's still-open scope column (GraphQL remains separately unstarted).
- New, real dependency is narrowly scoped (`rdflib` alone, in the existing `interop` extra) and does not touch any code path outside the optional interop surface — `schema/rdf.py` is not imported from `schema/__init__.py`, `rdf_exporter.py` is not imported from `plugins/reference/__init__.py`, matching the established opt-in pattern the LinkML bridge already set.
- `ReadOnlyView.schema()` is a small, generically useful addition beyond this one plugin's needs — any future schema-aware reference plugin (or third-party plugin) can use it too.

**Negative / follow-ups:**
- **No `from_owl` import direction.** Explicitly deferred, not silently dropped — a future KI/ADR would need to scope how much of arbitrary external OWL's expressivity this bridge should even attempt to understand, mirroring ADR-0013's own "documented subset, not full conformance" framing for whichever OWL constructs are supported.
- **IRI scheme does not honor a LinkML-imported schema's own declared `default_prefix`/`prefixes`.** A schema round-tripped through the LinkML bridge and then exported to RDF/OWL gets Ontolith's own `urn:ontolith:...` IRIs, not IRIs under whatever base the original LinkML source declared. Reasonable follow-up if a real interop scenario needs it; not implemented here.
- **No entity-driven export path** — only entities with at least one active assertion appear as RDF individuals (an entity with zero active assertions is never a subject `RdfExporter` sees, since it only iterates `kb.assertions()`). Matches `JsonExporter`'s own pre-existing scope exactly; not a new limitation this bridge introduces, but worth being explicit about since RDF/OWL consumers may expect every declared individual to appear regardless of whether it has any asserted properties yet.
- **`RdfExportReport.entities_written` counts entities that actually received an `rdf:type` triple, not every distinct subject probed** (found and fixed in review — an earlier version counted every subject added to a lookup-avoidance set, regardless of whether `kb.get_entity()` resolved it). The two are only distinguishable in the unreachable-in-practice case where a subject's entity somehow doesn't resolve (see the "No entity-driven export path" caveat above for the reachable asymmetry this method already documents).
- `owl:inverseOf` is emitted as a forward reference to the target concept's own `inverse`-named property IRI — the schema layer doesn't require both directions of a relation to independently declare `inverse` back at each other, so that property may not otherwise appear in the exported graph. **Both `to_owl()` and `RdfExporter` now declare every property/relation IRI they reference its own `owl:DatatypeProperty`/`owl:ObjectProperty` type regardless** (found in review: OWL 2 DL requires a declaration axiom for every IRI used as a property; an undeclared one silently demotes the ontology to OWL 2 Full, which most reasoners reject) — so the forward-referenced inverse IRI is declared even when the target concept doesn't otherwise mention it, and an active assertion under a predicate a later schema version removed (no migration/backfill mechanism exists, KI-048) is declared too, even though `to_owl()` alone only knows about the *current* schema's predicates.
- **`cardinality="single"` maps to `owl:FunctionalProperty` only when `temporality="static"` too** (found and fixed in review — an earlier version of this bridge applied it whenever `cardinality="single"` regardless of temporality). SPEC §10.2/bitemporal.md allow multiple simultaneously-`active` assertions on a `time_varying` predicate when their validity windows don't overlap (e.g. employment history) — declaring such a property `owl:FunctionalProperty` unconditionally would assert a real OWL logical inconsistency (two literals on a functional datatype property) for a state this codebase's own bitemporal model considers entirely valid, and a reasoner given the exported ontology plus that data would report it unsatisfiable.
- **This export has no representation of valid time at all — a real limitation, not previously stated.** Every currently-active assertion becomes exactly one triple; `confidence`, full provenance, `valid_from`/`valid_to`, and `status` are all dropped (unlike `JsonExporter`, which preserves them via `model_dump()`). For a governance-first, bitemporal KB this is the single most surprising property of the resulting artifact — a consumer treating the exported ontology as a complete picture of the KB's knowledge loses everything SPEC §11 (bitemporal reconstruction) and §5.3 (provenance) guarantee inside Ontolith itself. Acceptable for v1 (an OWL/RDF individual has no native slot for any of this without inventing reified statements or named graphs, a substantially larger design), but worth stating plainly rather than leaving implicit.
- **IRI components are now percent-encoded** (found and fixed in review — an earlier version of `base_iri`/`iri_for_*` embedded `namespace`/concept/predicate/entity-id strings unescaped). `SchemaIR`'s IR has no character-set validation on any name field, and a LinkML-imported schema (`schema/linkml.py::from_yaml`) takes names verbatim from YAML keys — idiomatic LinkML style uses space-separated class names and a URL `id:`, either of which broke unescaped `urn:`/Turtle IRI syntax and made `graph.serialize()` raise a bare `Exception` with no connection to the actual cause. `urllib.parse.quote(component, safe="")` is applied to every name component before embedding (dots in dotted predicates survive — always left unescaped, RFC 3986 unreserved), closing this for every caller of this module's IRI helpers, including the exact LinkML-import chain SPEC §13.3 names as this bridge's stated precedent.
- **Divergent `Float` mapping from the LinkML bridge, not reconciled.** `schema/linkml.py` maps `value_type="Float"` to LinkML range `"float"` (which real LinkML tooling would in turn map to `xsd:float`, 32-bit); this bridge maps the same `value_type` directly to `xsd:double` (64-bit, matching Python's own `float` representation exactly). `xsd:double` is the more accurate choice for what Ontolith actually stores, but the two bridges now describe the identical value_type with two different XSD datatypes if compared side by side. Not reconciled here — changing `linkml.py`'s existing, already-shipped mapping is a separate, unrelated change outside this ADR's scope.
- **A *retyped* predicate (still declared, but as a relation where a schema version previously declared it a property, or vice versa — `apply_schema` doesn't reject this) is not made OWL 2 DL-valid by the property-declaration fix above.** An old literal assertion under a predicate now schema-declared a relation still gets declared `owl:DatatypeProperty` (from the assertion's own `value_kind`) alongside `owl:ObjectProperty` (from `to_owl()`'s current-schema read) — punning between the two is itself prohibited in OWL 2 DL. Not a regression this fix introduces (that data was already non-DL-valid before it — a literal object under a schema-declared `owl:ObjectProperty`), and the root cause is the same KI-048 gap (no migration/backfill mechanism) as the removed-predicate case the fix does close; just not fully closed by it.
- **`Ontology` gains a new public `schema()` method** (mirroring the existing `AsOfView.schema()`) so `ReadOnlyView.schema()` could delegate to it rather than reaching into the storage port directly (found in review — an earlier version of `ReadOnlyView.schema()` did exactly that, the only view method to do so). Purely additive, no behavior change to any existing caller.

## Alternatives Considered

- **Depend on the real `linkml`/`linkml-runtime` packages, delegating literally to LinkML's own RDF generator** (the most literal reading of SPEC §13.3's "MAY initially delegate to LinkML's RDF emission"): rejected — reopens the exact dependency-weight tradeoff ADR-0013 already decided against for the adjacent bridge, for a feature that doesn't actually need LinkML's own schema-processing machinery (this bridge starts from `SchemaIR`, not a LinkML `SchemaDefinition`).
- **Hand-roll Turtle/RDF-XML text, no new dependency** (mirroring `to_yaml`'s own approach): rejected — RDF/OWL's correctness surface (URI escaping, datatype tagging, prefix consistency) is meaningfully riskier to hand-roll correctly than YAML's, and `rdflib` alone is a proportionate, narrowly-scoped cost to avoid that risk entirely.
- **Schema-only v1** (mirroring `to_yaml`'s exact scope, deferring instance data to a follow-up): considered and initially the recommended default; the user confirmed the broader schema-plus-instance-data scope directly, judging the added implementation cost proportionate to the more complete, more immediately useful deliverable.
- **Consult `metadata["prefixes"]`/`["default_prefix"]` for IRI minting from the start:** rejected for v1 — see Rationale; the metadata's own "not interpreted" framing (ADR-0013) makes this a real, separate feature, not a natural extension of the deterministic `urn:` scheme.
